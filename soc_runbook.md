# SOC Analyst Runbook

**Elastic SIEM — Credential Stuffing, DNS Tunneling, PowerShell Exploitation**

This runbook provides triage and investigation steps for analysts responding to alerts generated by the detection rules in this project. Each section covers alert context, initial triage, investigation queries, escalation criteria, and containment actions.

---

## Alert 1 — Credential Stuffing: Failed Logins from Single IP

**Rule:** `credential_stuffing_threshold.ndjson`
**Trigger:** ≥20 `event.outcome: failure` events from same `source.ip` within 5 minutes
**Severity:** High | **MITRE:** T1110 Brute Force

### Initial Triage

1. Note the `source.ip` from the alert detail
2. Check whether the IP is internal or external
3. Review the time window — is this activity ongoing?

### Investigation Queries (Kibana Discover)

**Check total failures from this IP:**
```
source.ip: "<attacker_ip>" and event.outcome: "failure"
```

**Check if any successful login followed:**
```
source.ip: "<attacker_ip>" and event.outcome: "success"
```

**Check what usernames were targeted:**
```
source.ip: "<attacker_ip>" | stats count by user.name
```

### Escalation Criteria

- Escalate **immediately** if a `success` event is found following the failures from the same IP
- Escalate if the source IP is external (internet-facing attack)
- Escalate if multiple usernames are being targeted (list-based stuffing)

### Containment Actions

- Block source IP at firewall / WAF
- Lock affected user accounts pending review
- Review auth.log for full activity scope
- If compromise confirmed: initiate password reset, session revocation, notify account owner

## Alert 2 — Credential Stuffing: Failure Followed by Successful Login

**Rule:** `credential_stuffing_sequence.eql.ndjson`
**Trigger:** `failure` → `success` sequence from same `source.ip` + `user.name` within 5 minutes
**Severity:** High | **MITRE:** T1110 Brute Force

> This alert indicates **probable account compromise**. Treat as confirmed incident until disproven.

### Initial Triage

1. Identify the `user.name` and `source.ip` from the alert
2. Confirm the success event timestamp — is the session still active?
3. Determine whether the login IP matches the user's known locations

### Investigation Queries

**Full login history for this user:**
```
user.name: "<username>" and event.category: "authentication"
```

**All activity from the attacker IP:**
```
source.ip: "<attacker_ip>"
```

**Check for any post-login actions (if application-level logging available):**
```
user.name: "<username>" and event.outcome: "success" | sort @timestamp desc
```

### Escalation Criteria

- Escalate immediately — this is a confirmed sequence indicating account compromise
- Notify the account owner to verify whether the login was legitimate

### Containment Actions

- Force logout / invalidate active session token
- Reset account credentials
- Block attacker IP at perimeter
- Preserve auth.log entries as evidence
- Open incident ticket; notify application owner

## Alert 3 — DNS Tunneling: Abnormal Query Volume

**Rule:** `dns_tunneling_volume_threshold.ndjson`
**Trigger:** ≥50 DNS queries from single `source.ip` within 5 minutes
**Severity:** High | **MITRE:** T1071.004

### Initial Triage

1. Identify the `source.ip` generating the volume
2. Check the DNS query names — are they sequential subdomains? Unusually long? Random-looking?
3. Check the response codes — high NXDOMAIN ratio is suspicious

### Investigation Queries

**All DNS events from the source host:**
```
source.ip: "<host_ip>" and event.category: "network" and dns.question.name: *
```

**Check for sequential subdomain pattern:**
```
source.ip: "<host_ip>" and dns.question.name: *.testlab.com
```

**NXDOMAIN ratio check:**
```
source.ip: "<host_ip>" and dns.response_code: "NXDOMAIN"
```

**Check destination resolver IPs (unusual external resolvers = red flag):**
```
source.ip: "<host_ip>" | stats count by destination.ip
```

### Escalation Criteria

- Escalate if destination resolver is an external non-standard IP (not corporate DNS / 8.8.8.8)
- Escalate if subdomains follow encoded/base64 patterns (e.g., `aGVsbG8=.example.com`)
- Escalate if volume exceeds 200+ queries in the window

### Containment Actions

- Block the suspicious domain pattern at DNS firewall / RPZ
- Isolate the host from the network if active tunneling is confirmed
- Capture a network trace (PCAP) from the host for deeper analysis
- Identify the process generating DNS queries (use endpoint telemetry)

## Alert 4 — PowerShell: Suspicious Execution Keywords

**Rule:** `powershell_suspicious_args.ndjson`
**Trigger:** Event ID 4104 with keywords: `TCPClient`, `IEX`, `DownloadString`, `bypass`, etc.
**Severity:** High | **MITRE:** T1059.001

### Initial Triage

1. Retrieve `powershell.file.script_block_text` from the alert / Discover
2. Identify the full command — note the destination IP/domain if present
3. Check `user.name` and `host.name` — is this an admin performing legitimate work?

### Investigation Queries

**Full script block content:**
```
event.code: "4104" and host.name: "<hostname>" | sort @timestamp desc
```

**Check for outbound network connection from same host around the same time:**
```
host.name: "<hostname>" and network.direction: "outbound" and process.name: "powershell.exe"
```

**Check if any payloads were downloaded:**
```
host.name: "<hostname>" and powershell.file.script_block_text: "DownloadString"
```

### Escalation Criteria

- Escalate immediately if a `TCPClient` or `DownloadString` command is found
- Escalate if an outbound network connection from PowerShell is confirmed within 30 seconds of the script block (see `powershell_network_correlation.eql.ndjson`)
- Escalate if the command is base64-encoded (`-enc` or `FromBase64String`)

### Containment Actions

- Isolate the host from the network
- Kill the PowerShell process (if active session)
- Investigate whether the reverse shell listener IP is reachable from your network
- Collect full memory dump / forensic image if compromise is confirmed
- Review recently downloaded files and new processes spawned from PowerShell

## General Notes

- All timestamps in Kibana are UTC — convert to local time when communicating with stakeholders
- Alert risk scores: 70–74 = High, 75–84 = High (elevated), 85+ = Critical
- When in doubt, isolate first and investigate second — containment is faster to undo than remediation
- Log evidence should be exported and preserved before any containment action that might affect log sources
